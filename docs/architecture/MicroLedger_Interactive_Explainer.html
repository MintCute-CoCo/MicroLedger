Core Data Lifecycle & Invariants

MicroLedger uses strict relational invariants in PostgreSQL. See how key business entities are created, transformed, and maintained append-only.

The Invariant Ledger

Inventory Movements

MicroLedger eliminates "stock drift" by forbidding unrecorded stock quantity edits.

  • Creation: Triggered whenever sales occur, PO stock arrives, or physical counts are adjusted.
  • Constraint: SUM(quantity_change) across all movement rows strictly matches products.stock_qty.
  • Immutability: The PostgreSQL app_user role has REVOKE UPDATE, DELETE ON inventory_movements.
Transaction Snapshot

Sales & Line Item Snapshots

Historical receipts must never mutate even if a product is subsequently renamed or repriced.

  • Snapshots: sku_snapshot and name_snapshot copy exact product details into sale_items at purchase time.
  • Idempotency: idempotency_key column prevents double-charges during WiFi reconnections.
  • Void Policy: Voiding a sale does not delete it; status becomes 'voided', restoring stock via compensating movement.
Audit & Accountability

Audit Logs & PII Redaction

Forensic tracking of every administrative action.

  • Written In-Transaction: An audit record is committed inside the exact same database transaction as the business event.
  • Redaction: Passwords, JWT tokens, and sensitive customer PII are strictly redacted before writing to audit_logs.

Edge Cases & Failure Handling

      
Enterprise POS systems face tough real-world conditions: hardware contention, flaky network drops, and unauthorized actions. Here is how MicroLedger guarantees safety.


      

        

          
1. Race Condition: Two Cashiers Ring Up the Last Single Item

          
Scenario: Product stock is 1. Cashier A and Cashier B tap "Complete Sale" at the exact same millisecond.

          
How MicroLedger Solves It:
            lockSaleProducts(trx, ids) executes SELECT ... FOR UPDATE ORDER BY id ASC. PostgreSQL puts a row lock on the product for Cashier A's transaction. Cashier B's transaction is paused in queue. Cashier A deducts stock to 0 and commits. Cashier B unblocks, reads stock = 0, and receives HTTP 409 Conflict: INSUFFICIENT_STOCK. Stock never drops below zero.
          

        


        

          
2. Flaky WiFi / Double-Submit

          
Scenario: Cashier taps checkout. The backend creates the sale, but before the HTTP 201 response returns to the browser, the store WiFi drops.

          
How MicroLedger Solves It:
            The frontend generates a unique UUID v4 Idempotency-Key for the cart. When the connection re-establishes and the request retries, the backend detects the duplicate key via findSaleByIdempotencyKey and immediately returns the completed sale receipt without deducting stock again or creating a duplicate invoice.
          

        


        

          
3. Brute-Force Password Guessing

          
Scenario: An attacker tries multiple password guesses on the admin login screen.

          
How MicroLedger Solves It:
            The authentication service tracks failed attempts per user account. Upon the 5th consecutive failed password attempt, the user record is locked for 15 minutes, returning HTTP 423 Locked.

Key Terms Made Simple

          

            

              
Idempotency

              
An operation that produces the exact same outcome no matter how many times it is repeated with the same key (prevents double-charges).

            

            

              
Row-Level Locking (FOR UPDATE)

              
Telling the database: "I am working on this specific row. Make all other transactions wait until I am finished."

            

            

              
Append-Only Ledger

              
A ledger where records are only inserted, never updated or deleted. Corrections are made via new compensating entries.

            

            

              
RBAC (Role-Based Access Control)

              
Restricting features based on user job role (e.g. Staff cannot view supplier wholesale costs or void sales; Admins can).
